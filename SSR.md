# Запуск и проверка SSR

Карточки товаров и отдельные страницы услуг рендерятся на сервере через Vike. Существующие URL и клиентская навигация React Router сохранены. Остальные страницы работают как SPA; сервер отдаёт их Title, Description, canonical и социальные метатеги. После перехода внутри сайта метатеги обновляются и очищают данные предыдущей страницы.

## Окружение

Нужен Node.js 22.18+; Dockerfile использует Node.js 24. Скопировать `.env.example` в `.env` и указать:

- `SITE_URL` — публичный origin сайта, например `https://example.com`, без пути. Совпадает с `SITE_URL` в API. Используется во всех canonical, Open Graph и sitemap.
- `API_SERVER_URL` — origin NestJS, доступный с сервера фронтенда, без `/api`, например `http://backend:3001`.
- `PORT` — порт production-сервера фронтенда, по умолчанию 3000.
- `HOST` — интерфейс production-сервера, по умолчанию `0.0.0.0`.
- `VITE_API_URL=/api`, пустой `VITE_IMAGES_API_URL` — браузер обращается к API и изображениям через тот же origin. При необходимости можно задать отдельные публичные адреса.

Vite-переменные `VITE_*` подставляются при сборке. В них нельзя помещать пароли, JWT_SECRET и другие секреты. `SITE_URL` и `API_SERVER_URL` читаются сервером при запуске; изменив их, перезапустить процесс.

```sh
npm ci
npm run dev -- --host 127.0.0.1 --port 3000

npm run build
npm start
```

Production-сборка запускается командой `node dist/server/index.mjs` и обслуживает `dist/client`. Раздачи одного статического `index.html` через nginx для SSR недостаточно. В Docker контейнер фронтенда слушает порт 3000; внешнему nginx/прокси нужно направлять запросы к этому Node-серверу. Старый `nginx/conf.d/default.conf` больше не используется Dockerfile.

Фронтенд проксирует `/api/*`, `/uploads/*`, `/sitemap.xml`, `/sitemaps/*` и `/robots.txt` в NestJS. Существующий внешний прокси может направлять эти маршруты непосредственно в API. Применить миграции API перед проверкой. Действующие секреты и домены передать контейнерам через окружение; локальные `.env` не входят в Docker-образ.

## SEO и данные

- Sitemap генерируется NestJS из базы: товары, услуги, категории и восемь публичных страниц. Приватные страницы и варианты фильтров не включаются. Для больших каталогов автоматически создаётся sitemap index с частями по 45 000 URL.
- `lastmod` товаров и услуг соответствует `updatedAt`. У страниц без достоверной даты `lastmod` отсутствует.
- URL товара без подкатегории: `/catalog/:categorySlug/product/:productSlug`. Текущие URL с подкатегорией сохранены. Неверная категория в URL существующего товара перенаправляет на его актуальный адрес через 301.
- Неизвестные карточки и страницы возвращают 404; недоступность API при SSR — 503. Ошибочные ответы имеют `noindex`. Корзина, админка и варианты фильтров также исключены из индексации. Категории и страницы пагинации имеют собственный canonical.
- Описания девяти категорий обновляются миграцией `20260907220000_category_descriptions`; при свежем импорте те же тексты использует seed.
- Старые HTML-обозначения единиц выводятся как текст: `м<sup>3</sup>` → `м³`. Произвольный HTML из характеристик не выполняется.

## Мессенджеры

`VITE_MESSENGER_PHONE` пока содержит `+7 (000) 000-00-00`. Кнопка без настроенного адреса открывает эту заглушку. Подставить номер или реальные `VITE_TELEGRAM_URL` / `VITE_WHATSAPP_URL`; для MAX указать `VITE_MAX_URL` профиля. Полный URL имеет приоритет над номером. После изменения `VITE_*` пересобрать фронтенд.

Примечание о Meta в подвале составлено с учётом [перечня Минюста](https://www.minjust.gov.ru/ru/documents/7822/): решение о Facebook и Instagram не распространяется на WhatsApp.

## Проверки

```sh
npm test
npm run lint
npm run build
```

В API: `npm run test:regression` проверяет сохранение файлов при последовательной загрузке и ошибках, удаление отдельных изображений, лимит 10 изображений, DTO и sitemap. После запуска проверить прямой HTTP-ответ карточки без JavaScript, переход между карточками, корзину после перезагрузки и редактирование товара в админке. У новой услуги должны появиться готовое содержимое в HTML и ссылка в sitemap; после удаления — 404 и отсутствие ссылки.

Локальные проверки выполняются на отдельной базе. Перенос на публичный сервер и проверка его прокси выполняются отдельно.
